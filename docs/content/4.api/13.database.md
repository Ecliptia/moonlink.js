#title
Database Class

#description
The Database class provides a simple key-value storage system for Moonlink.js, used internally to store player, node, and queue data.
<br>
```js
new Database(manager)
```
::

::alert{type="info" icon="lucide:info"}
The Database class is automatically initialized by the Manager and can be accessed through `manager.database`.
::

## File Storage

::card{icon="lucide:hard-drive"}
#title
File Storage System

#description
The Database class includes automatic file storage functionality.

#content
The Database automatically manages data persistence through JSON files:

- Files are stored in the `../datastore` directory relative to the Database class
- Each database instance has its own file named `data.{clientId}.json`
- Data is automatically loaded when the Database is initialized
- Data is automatically saved when modified using `set`, `push`, or `delete`

**File Structure**
```
moonlink.js/
  └── src/
      └── datastore/
          └── data.123456789.json
```

::alert{type="warning" icon="lucide:alert-triangle"}
The file storage system is handled automatically. You should not need to interact with the files directly.
::
::

## Usage Examples

::card{icon="lucide:code"}
#title
Basic Usage

#description
Examples of using the Database class.

#content
```js
// Access the database through the manager
const database = manager.database;

// Store player data
database.set(`players.${guildId}`, {
  volume: 100,
  paused: false,
  position: 0
});

// Retrieve player data
const playerData = database.get(`players.${guildId}`);

// Add a track to a queue
database.push(`queue.${guildId}`, track);

// Remove player data
database.delete(`players.${guildId}`);
```
::

## Best Practices

::card{icon="lucide:list-checks"}
#title
Best Practices

#description
Guidelines for using the Database class effectively.

#content
1. **Key Structure**
   - Use dot notation for nested keys (e.g., 'players.guildId.volume')
   - Keep keys organized by category (players, queues, settings, etc.)
   - Use consistent naming conventions

2. **Data Management**
   - Store only necessary data
   - Clean up old or unused data
   - Validate data before storing

3. **Error Handling**
   - Check if keys exist before accessing them
   - Handle undefined values appropriately
   - Use try-catch blocks when necessary

4. **Performance**
   - Avoid storing large objects
   - Don't store sensitive information
   - Clean up data when no longer needed
